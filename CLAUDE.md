# CLAUDE.md - CareerPredict AI

## What this is
A satirical 5-question career quiz web app: a Google-signed-in user gets a deterministic joke career title, fake stats and an AI-generated portrait; the audience is TODO(Roy): who is this for (portfolio showcase, friends, LinkedIn audience)?

Not an ML project. The "prediction" is a hand-written rule table (`mapCareer` in `server/careers.js`); the only real AI is the text-to-image call.

## Stack & layout
- `client/` - React 19, Vite 6, Tailwind 4, React Router 7 (data router, so `viewTransition` works), Motion via `LazyMotion` + `m.*` (strict: a full `motion.*` throws). Dev server on :3000 proxies `/auth` and `/api` to :5000 (`client/vite.config.js`).
  - `src/pages/` Landing, Onboarding (quiz), Loading ("Printing your cover"), Result (cover + report), Issues (`/issues`, "Your back issues" gallery; tapping a cover opens its page), IssuePage (`/issues/:id`, one back issue in full: cover, report, "Make this my current issue", Download, and "Put your face on it" for that issue; the current issue redirects to `/result`), NotFound. Signed-in pages are lazy routes in `App.jsx`.
  - `src/components/Cover.jsx` + `src/lib/coverCanvas.js` - the magazine cover on screen and as a 1080x1350 PNG; both read proportions from `src/lib/coverLayout.js`, so change sizes there, not in either renderer.
  - `src/lib/api.js` (all server calls), `src/lib/quiz.js` (drops draft answers that are no longer options), `src/lib/storage.js` (sessionStorage, never throws), `src/hooks/useImageReady.js` (HEAD-polls `/api/image/:id`), `src/content.js` (all copy, quiz options, and `FINDINGS`: the analyst's line printed under each quoted answer in the report; one per option, enforced by `lib/__tests__/content.test.js`).
  - `src/components/effects/` - the signature effects, each self-contained with a fallback: `HalftoneReveal` (CMYK halftone press reveal, Paper Shaders WebGL2, lazy chunk), `TiltCard` (pointer tilt + gloss), `Stamp` (ink rubber stamp on the report, never on the cover), `Odometer`, `EffectBoundary` (an effect that throws removes itself, never the page). `hooks/useProximityWeight.js` drives the hero's variable-weight letters. CSS-only effects (CMYK misregistration, print head, barcode laser) live in `index.css` under "Print shop effects". Every effect checks `lib/capabilities.js` (WebGL2, hover) and reduced motion first.
  - `src/components/IssueRack.jsx` - the landing page's "Back issues": the sample covers standing side by side like a newsstand rack, a horizontal scroll-snap row (swipe on a phone, the next cover peeking in; arrow buttons on wider screens, direction-aware in RTL), a focusable labelled region, no scroll pinning. It replaced a scroll-driven fan where only the front cover was readable. Two effects, both off under reduced motion: centre focus (the middle cover straight and lit, neighbours turned toward it, smaller and dimmer, written per scroll frame straight to the wrappers' style) and off the press (each cover's first time in view runs the halftone press, at most `MAX_PRESSES` = 2 at once, staggered, at `pressPace` 0.6; a cover waiting its turn glows in the darkroom via `Cover`'s `pressReady`).
  - The masthead logo links to `/` with `state.home`, which stops `Landing` from sending a signed-in reader to `/result` (it still does on arrival, so a returning visitor lands on their cover); signed in, the hero offers "Back to your cover" instead of Google sign-in.
  - Fonts: `src/fonts.css` + `src/assets/fonts/` are generated by `client/scripts/trim-fonts.py` from the fontsource packages, with the weight axis cut to what the site uses (Newsreader 400-720, italic 400-600, Schibsted 400-800; ~21% less on a first visit). Hebrew: Frank Ruhl Libre and Heebo, Hebrew subset only, second in each stack, so they download only when Hebrew is on the page (~24 KB). Using a weight outside those ranges means editing `FACES` in the script and re-running it (`pip install fonttools brotli`).
  - Hebrew edition (`src/i18n/`): `LangProvider` / `useLang()` / `useCopy()` in `LangContext.jsx`; the toggle is in `Masthead`; the choice is saved in localStorage, the default follows the browser language, and an inline script in `index.html` sets `<html lang dir>` before first paint. UI text lives in `ui.en.js` / `ui.he.js` (same shape, checked by `lib/__tests__/i18n.test.js`), questionnaire copy in `quiz.he.js`, career copy in `careers.he.js` (keyed by English title, `title` / `titleF`), read through `i18n/content.js`. The English option text stays the value stored and sent to the server; Hebrew is display only, matched by position. Hebrew job titles are gendered: the server sends `coverGender` (`coverGenderFor` in `careers.js`: the photographer's choice, else the scene's subject, null for your own photo). Errors are raised in English and translated at display by `lib/errors.js`; the i18n test fails if any message in `server/` or `client/src/lib/` lacks a Hebrew entry. Layout uses logical classes (`ms-`, `ps-`, `text-start`, `rtl:`); the cover PNG mirrors in Hebrew (`coverCanvas.js`). Copy is gender-neutral: plural address in UI, impersonal captions.
  - Page titles: per language in `ui.*.js` `pageTitles`, set per route via `handle.title` (a key) in `App.jsx`, where `usePageChange` also moves focus to `<main>` on every client-side navigation (screen readers announce the page).
  - Design tokens in `src/index.css` `@theme`: paper / ink / one highlighter (`mark`). Rationale and the review against Anthropic's frontend-design skill: `docs/redesign-plan.md`.
- `server/` - Express 4 monolith (CommonJS), Passport Google OAuth, express-session (memory store), SQLite via `@libsql/client`: Turso in production (`TURSO_DATABASE_URL`, `TURSO_AUTH_TOKEN`), a local file otherwise.
  - `index.js` - entry; waits for `initDB()`, then mounts routes and serves `client/dist` with an SPA catch-all.
  - `db.js` - async API over libsql; schema + additive migrations via `addColumnIfMissing` (checks `PRAGMA table_info`). `saveOnboarding` replaces the user's current row and archives the same cover in `covers` ("Your back issues", last 30 per user, pruned in the same write batch). Existing results are imported into `covers` once at startup. Tested against a real SQLite file in `__tests__/db.test.js`, including the schema production Turso had before `image_id`.
  - `asyncRoute.js` - wraps every async Express handler so a rejection becomes a JSON 500 (Express 4 would hang the request).
  - `userData.js` - pure edge helpers: `profileToUserFields` (Google profile in), `toPublicUser` (whitelist for `/auth/me`), `validateOnboardingAnswers`. Tested in `server/__tests__/`.
  - `quiz.js` - the answer catalog: option text the client sends to stable option ids. `__tests__/quiz.test.js` imports `client/src/content.js` and fails if the two copies differ by a character.
  - `careers.js` - `CAREERS` table (40 careers, 10 per field, each with two cue option ids) and `mapCareer`: the tabs answer picks the field's shelf, the career matching most cues wins, an FNV hash of the option ids breaks ties; returns `evidence` (two of the user's answers, quoted on the report). Plus `SAMPLE_ANSWERS` for the landing page. Pure, tested in `__tests__/careers.test.js` (all reachable, each 1-4% of the 1,024 answer sets). Rationale: `docs/quiz-redesign.md`.
  - `routes/userRoutes.js` - `/api/user/onboarding`, `/api/user/result`, `GET /api/user/covers` and `DELETE /api/user/covers/:id` (back issues; each cover carries its career's current shared scene, kicked off idempotently, plus `personalImageUrl` when the reader shot their own portrait for that issue; removing an issue deletes that portrait, and the current issue can't be removed, 409), `GET /api/user/covers/:id` (one back issue with its report, for IssuePage), `POST/DELETE /api/user/covers/:id/portrait` (the reader's own face on one back issue, consent v2 only, same limits as `/portrait`; 409 for the current issue, whose portrait belongs to the result page), and `POST /api/user/covers/:id/current` ("choose your issue": the back issue becomes the current result again and moves to the top of the archive, keeping its filing date and its personal portrait; the replaced result is handled like a retake). Loading a result calls `kickoff` for its career's current scene (idempotent), so a portrait lost in a deploy, whose stopgap expired or whose prompt changed is regenerated, and the row is repointed to the new id.
  - `routes/shareRoutes.js` - public share links (`docs/share-page.md`): `POST/PATCH/DELETE /api/user/share` (one-tap sharing: the browser names the token so the share sheet opens inside the tap; PATCH switches the face on a sent link; DELETE ends every link of the issue), public `GET /api/share/:token` (+ `/image`, `/og.jpg`), and `GET /s/:token`, which serves the SPA's `index.html` with link-preview tags written in (mounted before the static files and catch-all). Snapshots live in the `shares` table; the owner's face only on opt-in; `unlinkSharedPortrait` runs whenever a personal portrait is deleted. `portraitUrl.js` is the shared-portrait URL helper used by the covers and share routes. Client: `pages/SharePage.jsx` (public route), `components/SharePanel.jsx` (`useShareLink` + the strip under the result page's buttons), `components/Report.jsx` (the report, shared by both pages).
  - `routes/sampleRoutes.js` - public `GET /api/samples`: the fixed landing-page samples with portrait URLs (kicks off generation, cached). `imageUrl.js` builds absolute image URLs for both routes.
  - `routes/imageRoutes.js` - `GET /api/image/:id` (16-hex id; 404 + `Retry-After: 8` while generating).
  - Personal portraits (the user's own face, opt-in; `docs/personal-portrait.md`): `POST/DELETE /api/user/portrait` and owner-only `GET /api/user/portrait/image/:id` in `userRoutes.js`; `routes/refRoutes.js` serves the uploaded photo to the model at `/api/ref/:token`; `photoUpload.js` (validate, strip metadata), `rateLimit.js`, `services/image/personalPortraits.js` + `referencePhotos.js`. Client: `components/PersonalPortrait.jsx`, `PhotoConsent.jsx` (consent, then "Take a selfie" or "Choose a photo"), `CameraCapture.jsx`, `lib/photo.js`. "Take a selfie" follows `cameraMode()` (`lib/capabilities.js`): on a touch device an `<input capture="user">` opens the phone's own front camera; on a computer an in-page viewfinder (`getUserMedia`, https only) that releases the camera on every way out; neither, and only the file picker shows. A shot goes through the same `preparePhoto` path as a chosen file.
  - `services/image/` - `ImageService` orchestrator (sync `kickoff`, in-flight dedup, fallback cascade), `promptBuilder` (seed, SDXL/FLUX dialects, content-hash id), `providers/` (realvisxl, cloudflare, huggingface_flux, together, pollinations), `storage/` (disk, r2, turso, plus `WebpStore`, which wraps whichever backend and re-encodes portraits as WebP), `__tests__/`.
- `docs/image-service-spec.md` - contract the image pipeline and its tests satisfy.
- `.github/workflows/test.yml` (server tests on push/PR), `keep-alive.yml` (pings Render every 14 min).
- Deploy: Render single service, https://career-predictor-cnvg.onrender.com, deploying `main` (`render.yaml`). Until November 2026 the dashboard deployed a separate branch (`claude/migrate-free-hosting-tvidw`, the Turso migration), so merges to main did not ship; check the service's branch if a merge doesn't appear.

## Commands
- Server tests: `cd server && npm test` (node:test; runs `server/__tests__/` and `services/image/__tests__/`) - verified, 201/201 pass on Node 22 after `npm install`.
- Client tests: `cd client && npm test` (node:test over pure modules in `src/lib/__tests__/`) - verified, 39/39 pass.
- Client build: `cd client && npx vite build` - verified. CI (`test.yml`) runs server tests, client tests and the client build.
- Likeness test for the planned personal portrait: `cd server && npm run check:likeness` (needs `POLLINATIONS_API_KEY`; spends pollen; writes an HTML contact sheet). Plan and pass criteria: `docs/personal-portrait.md`. Unverified against the real API (no key in the dev container).
- Image key check: `cd server && npm run check:image` (add `-- --generate` for one real render) - verified against a fake key (clean 401) and a missing key. Owner steps: `docs/pollinations-setup.md`.
- Server dev: `cd server && npm install && npm run dev` (nodemon, :5000) - unverified.
- Client dev: `cd client && npm install && npm run dev` (:3000) - unverified.
- Prod build: `npm run build` at root (installs both, builds client) - unverified.
- Prod start: `npm start` at root (`node server/index.js`) - unverified.
- Config: copy `server/.env.example` to `server/.env`. Default image chain is `pollinations` (keyless), which now always serves the low-end "sana" model with a watermark; setting `POLLINATIONS_API_KEY` (an `sk_` key) switches the default to `pollinations_gen,pollinations`.

## Conventions (Roy's standing rules)
- Comments explain WHY, not what.
- Flag counterintuitive, load-bearing or past-bug-hiding lines with `// don't touch / <reason>`.
- Edge cases and input validation are priorities; prefer clean OOP, good naming, reuse.
- No em dashes in any user-facing text or docs; use a plain hyphen.
- Secrets only via environment variables, never committed.
- New image provider or store = one new file + one factory entry in `providers/index.js` or `storage/index.js`, plus a test in `__tests__/`. Do not touch the route or orchestrator for that.
- `kickoff()` must stay synchronous (no `await` before return); spec section 2 and `imageService.test.js` enforce it.

## Gotchas
- Copy changes come in pairs: editing English text in `ui.en.js`, `content.js` (options, findings, notes) or a career means editing its Hebrew in `ui.he.js`, `quiz.he.js` or `careers.he.js`; the tests catch missing keys and careers, not stale meaning.
- Quiz option text lives twice, `client/src/content.js` and `server/quiz.js`, and must match exactly (the client sends text, the server maps it to an id); `quiz.test.js` enforces it, so edit both together. The server rejects any answer that is not a current option with "The questionnaire was updated. Reload the page and answer again." (`validateOnboardingAnswers`), and the client drops stale draft answers (`lib/quiz.js`). Question ids are DB column names and keep their old names (`strength` holds the dead-laptop answer).
- `getImageService()` runs inside `initDB().then(...)` in `server/index.js`, so a provider missing its key fails startup via the same catch (logged as "Startup failed ...").
- `LocalDiskStore` default dir and `IMAGE_CACHE_DIR=./data/image-cache` resolve against `process.cwd()`. Root `npm start` writes to `<repo>/data/` (gitignored as `/data/`), not `server/data/`.
- Persistence: Render free-tier disk is wiped on redeploy. The database survives only because production uses Turso; without `TURSO_DATABASE_URL` it falls back to a local file that is lost on deploy. Portraits survive too: with `TURSO_DATABASE_URL` set, the image store defaults to `turso` (an `images` table in the same database; the log prints `[IMAGE] store: turso+webp`). Sessions still use the in-memory store and die on every restart.
- Pollen: the keyed Pollinations model costs ~0.004 pollen per portrait, and both keys are "Quest pollen only". When the account's Quest Pollen runs out (it did on 2026-11-04), `pollinations_gen` returns 402 and the chain falls back to the keyless, watermarked model. `ImageService` treats that fallback (a `provisional` provider that is not first in the chain) as a stopgap: it serves it from memory for 30 minutes and does not write it to the durable store, so the portrait is regenerated properly once pollen is back. Every prompt change means one new paid render per affected portrait.
- Each career has two scenes: `prompt` (subject `subject`) and `altPrompt` (the other gender), picked by the photographer's step (`portrait_subject`: woman / man / surprise / photo; surprise and photo keep `prompt`). "Use my own photo" (shown only when `GET /api/features` says personal portraits are on) opens the consent panel on that step; the selfie is held in memory (`lib/pendingPhoto.js`) and uploaded by `Loading.jsx` right after the result is saved, so the first cover the reader sees is already theirs. A reload drops it and the result page says so. `careers.test.js` checks the first standalone woman/man word of each scene matches, so keep the subject named in the first clause.
- Personal portraits need a public https `SERVER_URL` (the model fetches the photo from `/api/ref/:token`) and a key allowed to use the MAI Image models; otherwise `personalAvailable` is false and the panel hides. They can't be exercised end to end from a dev container (the model can't reach localhost); `__tests__/portraitRoutes.test.js` covers the flow with a fake model. The uploaded photo never touches disk or the database, by design: don't move `referencePhotos.js` to a persistent store. The finished portrait is kept per consent version, sent as `X-Portrait-Consent`: `yes` (v1, old tabs) is deleted on a retake as that wording promised; `v2` (current wording) is linked to its back issue (`covers.personal_image_id`) and kept until the reader removes the issue or the photo, or the 30-issue cap prunes it. Rate limits are in memory (single instance).
- Bandwidth: Render's free tier includes 5 GB outbound a month and, with no card on file, suspends the service for the rest of the month when it runs out. That is why every stored portrait is re-encoded as WebP (`storage/webpStore.js`, measured ~9% of the JPEG). Keep new image-heavy features on WebP and small sizes.
- Running scripts that call Pollinations from a dev container whose proxy injects the key: Node's built-in fetch ignores HTTPS_PROXY unless started with `NODE_USE_ENV_PROXY=1`.
- `SESSION_SECRET` falls back to a hardcoded dev string in `server/index.js` if unset (production logs a warning but still starts). Set it in every deployed env.
- `docs/image-service-spec.md` links to a `.claude/plans/...` file outside the repo (dead link).
- `@paper-design/shaders-react` must stay in `optimizeDeps.include` (`vite.config.js`): if Vite discovers it mid-session it pre-bundles a second React copy and the shader throws "Invalid hook call" (dev only). `HalftoneReveal`'s `size` is calibrated: 1 renders blurry blobs, ~0.55 is the coarsest that still reads as print dots.
- Client tests cover only pure modules (`src/lib`); pages are verified by hand / Playwright with a mocked API, there is no component test setup.
- Changing cues or the table changes which career a given answer set gets (saved results are unaffected, they are stored, evidence included). `careers.test.js` fails if a title becomes unreachable, any career leaves the 1-4% band, or a sample answer set stops matching its label; `quiz.test.js` fails if `client/src/content.js` `SAMPLE_TITLES` differs from `SAMPLE_ANSWERS` titles and order.
- `html` has `overflow-x: clip` (`index.css`, `don't touch`): one effect poking past the edge mid-animation made mobile browsers widen the layout viewport and the result page scrolled sideways for good. Keep effects inside their column anyway. The back-issue rack scrolls inside its own container, so it never widens the page.
- First-screen rule: on a 375x667 phone the quiz shows all four options, and the result page shows the cover, headline and Download / Share without scrolling. On a phone the caption sits below Download / Share (`max-sm:order-last` in `Result.jsx`): above the row, one to four lines of caption pushed the buttons under the first screen for 39 of 40 careers. The result cover's width is the `cover-fit` utility (`index.css`), sized from the viewport height; its `18rem` (phone) and `8rem` (lg) are the height of everything else on that first screen, so retune them when the masthead, headline or action row grows. Measured with Playwright at 375x667, 390x664, 1366x768 and 1440x900.
- The quiz step lives in the URL (`/onboarding?q=3`) so browser Back works; `resolveStep` clamps it to the first unanswered question.
- The result page reads its sessionStorage copy (`cachedResult`) before fetching, so anything that changes the current result on the server must clear it: `makeCoverCurrent` in `lib/api.js` does (`don't touch`); before that, choosing a back issue left the result page showing the replaced issue.
- `Loading.jsx` snapshots the draft answers once on mount (marked `don't touch`): re-reading storage per render raced the deferred view-transition navigation and bounced users back to /onboarding.
- The cover export needs CORS on `/api/image/:id` in dev (different origins); `server/index.js` `cors()` covers it. If the canvas is tainted anyway, `renderCoverBlob` retries without the photo.
- `ImageService` output size is 896x1120 in production (`instance.js` `COVER_SIZE`); the constructor rejects sizes that are not multiples of 32 in [256, 1440].
